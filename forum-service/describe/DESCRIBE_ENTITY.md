# Сущности `forum-service`

## 1. Назначение и границы сервиса

`forum-service` хранит и изменяет содержимое форума: публикации, комментарии и
метаданные прикреплённых к публикациям файлов. Согласно архитектурной схеме,
сервис владеет собственной базой данных `forum_db`, получает необходимые данные
о пользователе из `profile-service` и публикует асинхронные события, в частности
`forum.post.created` и `forum.comment.created`.

В начальную модель входят три сущности:

1. `Post` — публикация пользователя и корень агрегата обсуждения.
2. `Comment` — сообщение в обсуждении публикации.
3. `Attachment` — метаданные файла, приложенного к публикации.

Такой набор покрывает основной сценарий форума: создать публикацию, при
необходимости приложить к ней файлы и вести обсуждение. Категории, теги,
реакции, подписки и отдельная модель модерации пока не включены, поскольку они
не представлены в исходной схеме и требуют самостоятельных бизнес-правил.

## 2. Общие решения

- Идентификаторы сущностей — UUID. Они подходят для независимого сервиса,
  безопасны для передачи через API и не требуют общего генератора
  последовательностей между экземплярами приложения.
- Все даты и время хранятся в UTC с часовым поясом. Это исключает неоднозначность
  при работе пользователей из разных часовых поясов.
- `authorId` содержит только идентификатор владельца из `profile-service`.
  Внешний ключ на таблицу профилей невозможен: данные принадлежат другому
  микросервису и другой базе данных.
- Имя, аватар и прочие сведения автора не являются частью доменных сущностей
  форума. Актуальные сведения запрашиваются у `profile-service`; если позднее
  потребуется устойчивое отображение при его недоступности, для этого следует
  создать отдельную локальную проекцию, обновляемую событиями.
- Удаление публикаций и комментариев является логическим. Это сохраняет
  целостность обсуждения, позволяет проводить аудит и не оставляет ответы без
  контекста.
- Состояния, имеющие фиксированный набор значений, задаются перечислениями, а не
  произвольными строками.

## 3. Сущность `Post`

Публикация является корнем агрегата: комментарии и вложения не существуют без
неё.

| Поле | Тип | Обязательность и ограничения | Назначение |
| --- | --- | --- | --- |
| `id` | UUID | Обязательно, первичный ключ | Уникальный идентификатор публикации. |
| `authorId` | UUID | Обязательно | Идентификатор автора в `profile-service`. |
| `title` | Строка до 200 символов | Обязательно, после удаления пробелов не пустая | Краткий заголовок для списков и поиска. Ограничение защищает API и интерфейс от чрезмерно длинных значений. |
| `content` | Текст | Обязательно, после удаления пробелов не пустой | Основное содержимое публикации. Текстовый тип не вводит искусственно малый предел на сообщение. |
| `status` | `PostStatus` | Обязательно | Управляет видимостью публикации без физического удаления. |
| `createdAt` | Дата и время | Обязательно, неизменяемо | Время создания для сортировки, аудита и события `forum.post.created`. |
| `updatedAt` | Дата и время | Обязательно | Время последнего изменения заголовка, содержимого или состояния. |
| `version` | Целое неотрицательное число | Обязательно | Версия для оптимистической блокировки, предотвращающая потерю параллельных изменений. |

### `PostStatus`

| Значение | Смысл |
| --- | --- |
| `PUBLISHED` | Публикация доступна для чтения и комментирования. |
| `DELETED` | Публикация логически удалена и её содержимое не выдаётся обычным пользователям. |

Для первой версии отдельное состояние черновика не требуется: в исходных
требованиях описана публикация сообщений, но не работа с черновиками. При
появлении такого сценария `DRAFT` можно добавить без изменения состава полей.

### Почему выбраны эти поля

`id`, `authorId`, `title` и `content` образуют минимально достаточное описание
публикации. `createdAt` и `updatedAt` нужны для обычной хронологии форума и
позволяют клиенту показать факт редактирования. Пара `status` и `version`
обеспечивает безопасное удаление и изменение данных. Вычисляемые показатели,
например число комментариев, не включены в источник истины: сначала их можно
получать запросом, а при доказанной проблеме производительности — хранить в
отдельной проекции.

## 4. Сущность `Comment`

Комментарий всегда относится к одной публикации. Модель поддерживает ответы на
комментарии любой глубины через необязательную ссылку на родительский
комментарий.

| Поле | Тип | Обязательность и ограничения | Назначение |
| --- | --- | --- | --- |
| `id` | UUID | Обязательно, первичный ключ | Уникальный идентификатор комментария. |
| `postId` | UUID | Обязательно, внешний ключ на `Post.id` | Публикация, внутри которой находится комментарий. |
| `authorId` | UUID | Обязательно | Идентификатор автора в `profile-service`. |
| `parentCommentId` | UUID | Необязательно, внешний ключ на `Comment.id` | Родительский комментарий для древовидного обсуждения; отсутствие значения означает комментарий верхнего уровня. |
| `content` | Текст | Обязательно, после удаления пробелов не пустой | Текст комментария. |
| `status` | `CommentStatus` | Обязательно | Позволяет скрыть содержимое, сохранив структуру ответов. |
| `createdAt` | Дата и время | Обязательно, неизменяемо | Время создания для сортировки и события `forum.comment.created`. |
| `updatedAt` | Дата и время | Обязательно | Время последнего изменения текста или состояния. |
| `version` | Целое неотрицательное число | Обязательно | Защита от потери параллельных изменений. |

### `CommentStatus`

| Значение | Смысл |
| --- | --- |
| `PUBLISHED` | Комментарий видим участникам обсуждения. |
| `DELETED` | Текст скрыт, но узел остаётся в дереве, чтобы сохранить ответы. |

### Инварианты комментария

- `postId` должен указывать на существующую публикацию со статусом `PUBLISHED`.
- Если указан `parentCommentId`, родитель должен существовать, принадлежать той
  же публикации и не совпадать с самим комментарием.
- Создание цикла в цепочке родителей запрещено.
- Новый комментарий нельзя добавить к логически удалённой публикации.
- При логическом удалении комментария его дочерние ответы не удаляются.

### Почему выбраны эти поля

Кроме идентификатора автора и текста комментарию необходим `postId`, поскольку
публикация задаёт границу обсуждения. `parentCommentId` даёт поддержку ответов
без отдельной сущности и без ограничения глубины дерева. Поля состояния, времени
и версии решают те же задачи сохранности истории и конкурентного изменения, что
и у публикации.

## 5. Сущность `Attachment`

Сам файл хранится во внешнем S3-совместимом хранилище, указанном на
архитектурной схеме. В `forum_db` сохраняются только сведения, необходимые для
связи файла с публикацией, отображения и безопасной загрузки.

| Поле | Тип | Обязательность и ограничения | Назначение |
| --- | --- | --- | --- |
| `id` | UUID | Обязательно, первичный ключ | Стабильный идентификатор вложения для API. |
| `postId` | UUID | Обязательно, внешний ключ на `Post.id` | Публикация-владелец файла. |
| `storageKey` | Строка до 1024 символов | Обязательно, уникально | Непубличный ключ объекта в S3-совместимом хранилище. |
| `originalFileName` | Строка до 255 символов | Обязательно | Исходное имя для отображения и скачивания; не используется как путь хранения. |
| `mediaType` | Строка до 255 символов | Обязательно | MIME-тип для корректной и безопасной отдачи файла. |
| `sizeBytes` | Целое 64-битное число | Обязательно, больше нуля | Размер для проверки лимитов и отображения пользователю. |
| `createdAt` | Дата и время | Обязательно, неизменяемо | Время регистрации вложения. |

### Почему выбраны эти поля

`postId` задаёт владельца и жизненный цикл вложения. `storageKey` отделён от
исходного имени: пользовательское имя может повторяться или содержать
небезопасные символы, а адрес объекта должен оставаться уникальным и внутренним.
`mediaType` и `sizeBytes` позволяют проверить ограничения до выдачи файла.
Публичный URL не хранится, поскольку он может меняться или быть временным;
сервис должен формировать ссылку на загрузку по `storageKey`.

Для комментариев вложения пока не предусмотрены: архитектурная схема
подтверждает наличие файлового хранилища, но не задаёт такой сценарий. Если он
появится, вместо двух необязательных ссылок на владельца лучше явно расширить
модель вложений с проверяемым типом владельца либо ввести отдельную сущность
вложения комментария.

## 6. Связи и правила жизненного цикла

- `Post` имеет от нуля до многих `Comment`.
- `Post` имеет от нуля до многих `Attachment`.
- `Comment` может иметь от нуля до многих дочерних `Comment`.
- `authorId` в `Post` и `Comment` является межсервисной ссылкой, но не внешним
  ключом базы данных.
- При логическом удалении публикации её комментарии и вложения перестают быть
  доступны через обычные пользовательские операции. Физическую очистку файлов
  из S3 следует выполнять отдельно и повторяемо, чтобы сбой внешнего хранилища не
  нарушал транзакцию в `forum_db`.
- События о создании публикации и комментария публикуются только после успешной
  фиксации соответствующей сущности. Для гарантированной доставки в дальнейшем
  следует использовать транзакционный outbox; его запись является технической
  моделью доставки событий, а не доменной сущностью форума.

## 7. Ограничения и индексы базы данных

Рекомендуемые ограничения:

- внешние ключи `Comment.postId` и `Attachment.postId` ссылаются на `Post.id`;
- `Comment.parentCommentId` ссылается на `Comment.id`;
- уникальное ограничение на `Attachment.storageKey`;
- проверки непустого `Post.title`, `Post.content` и `Comment.content`;
- проверка положительного значения `Attachment.sizeBytes`;
- проверка неотрицательного `version`.

Рекомендуемые индексы:

| Поля индекса | Для какого запроса |
| --- | --- |
| `Post(status, createdAt, id)` | Постраничная выдача опубликованных записей от новых к старым. |
| `Post(authorId, createdAt, id)` | Публикации конкретного автора. |
| `Comment(postId, parentCommentId, createdAt, id)` | Получение корневых комментариев или ответов одной ветки в стабильном порядке. |
| `Comment(authorId, createdAt, id)` | Комментарии конкретного автора. |
| `Attachment(postId)` | Все вложения публикации. |

`id` добавлен в сортировочные индексы как однозначный второй критерий: несколько
записей могут иметь одинаковое время создания. Это позволяет использовать
стабильную курсорную пагинацию.

## 8. Что намеренно не хранится

- Пароль, email, роли, имя и аватар пользователя принадлежат `auth-service` или
  `profile-service`.
- Бинарные данные вложения принадлежат S3-совместимому хранилищу.
- Готовые публичные ссылки на файлы не являются устойчивыми данными.
- Количество комментариев и другие счётчики являются производными значениями.
- Данные доставки уведомлений принадлежат `notification-service`.
- Категории, теги, реакции и подписки следует добавлять только после определения
  пользовательских сценариев и правил их жизненного цикла.

Такое разделение сохраняет владение данными внутри границ микросервисов и не
связывает `forum-service` общей схемой базы данных с остальными сервисами.
